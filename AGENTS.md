# Постоянные правила работы с Sanremo Russia

Эти правила действуют для всего репозитория и всех последующих задач.

## Перед любой работой

1. Полностью прочитать `AGENTS.md`, `PROJECT_STATE.md` и `PROJECT_HISTORY.md`.
2. Проверить `git status --short --branch`, текущую ветку, remotes и HEAD.
3. Для публикации или инфраструктурных изменений перечитать `DEPLOY.md`, `CONTENT-MAP.md` и навык `publish-bio-sites-timeweb`.
4. Проверить фактический staging, если задача относится к опубликованному поведению. Скриншот пользователя — свидетельство проблемы, но завершение подтверждается опубликованным сайтом.
5. Не начинать с предположения, что постоянная локальная `main` совпадает со staging. Сверить с `timeweb/main`.

## Источники истины

При конфликте использовать такой приоритет:

1. Явное актуальное указание пользователя.
2. Подтверждённые коммерческие данные BIO и официальные материалы Sanremo.
3. Опубликованное поведение staging и HEAD репозитория, подключённого к Timeweb.
4. `PROJECT_STATE.md` с датой и источником проверки.
5. Исходное ТЗ и другие локальные документы.
6. Старый код, макеты и тексты — только как исторический материал.

Не превращать предположения, временные значения, подписи макетов или автогенерированный текст в факты. Если источник не найден, писать «требует подтверждения».

## Git и публикация

- Источник staging на момент создания этого файла: `timeweb/main` репозитория `biotempbio/Sanremo_Site`. Перед каждым push подтвердить это повторно.
- `origin/main` репозитория `biotempbio/sanremo-russia-site` не считать источником staging без новой проверки.
- Push в подключённую к Timeweb ветку равен публикации. Не отправлять незавершённые изменения.
- Перед push выполнить минимум: `npm run build`, `npm run lint`, `npx tsc --noEmit`, `git diff --check`.
- После push дождаться фактической смены версии и проверить изменённые маршруты/ресурсы HTTP-запросом и, когда возможно, визуально в браузере.
- Не сообщать «опубликовано», пока staging не отдаёт новую версию.
- Не менять DNS, домены, `next.config.ts`, `NEXT_PUBLIC_SITE_URL`, маршруты или режим индексации в рамках обычной правки.
- Не удалять старую ChatGPT Sites-публикацию без прямого запроса: это резерв/preview.
- Не трогать пользовательские неотслеживаемые файлы и резервные каталоги. Не применять destructive Git-команды.

## Данные и контент

- Основной источник каталога, РРЦ, наличия, дилеров и запчастей: `data/catalog.json`; вычисления — `lib/catalog.ts`.
- Видимые тексты интерактивной главной часто находятся в `public/sanremo-russia.html`; оболочка — `app/page.tsx`.
- Логика подборщика: `app/choose/ChooserClient.tsx`; server-side подготовка данных: `app/choose/page.tsx`.
- Все названия сценариев и query-параметры с главной должны совпадать с подборщиком. После изменения проверить каждый вход с главной.
- Писать «на складе в Москве», если речь о российском складе BIO.
- Не публиковать внутренние оправдательные дисклеймеры и неподтверждённые обещания.
- Не публиковать число, цену, остаток, дилера, кейс или техническое свойство без проверяемого источника и даты.
- Для YOU сохранять подтверждённое позиционирование: компактная профессиональная high-end мультибойлерная машина; сценарии включают Specialty.

## Фото, логотип и дизайн

- Использовать официальный логотип Sanremo без перерисовки текстом; проверять резкость в браузере.
- Использовать только официальные или подтверждённые фото правильной модели/конфигурации. Не подменять реальное фото AI-изображением или случайным stock.
- Для каждого нового внешнего медиа фиксировать источник, дату получения и права/разрешение, если они доступны.
- Если браузер нестабильно загружает файл, проверить MIME, целостность и публичный URL; при замене использовать новый файл/URL и проверить опубликованную версию.
- Соблюдать утверждённое светлое модульное направление. Не возвращать кислотный жёлто-зелёный фон, декоративные диагональные стрелки, градиентные заглушки и другие отклонённые AI-клише.

## Проверка результата

- Проверять desktop и mobile для затронутых страниц.
- Для фильтров проверять не только выбранную кнопку, но и фактический список результатов после каждого шага.
- Для изображений проверять HTTP 200, корректный MIME и фактическую декодируемость файла.
- Для ссылок из iframe использовать абсолютный адрес текущего контура либо безопасную навигацию, которая не разрешается относительно `file:` оболочки.
- Не просить пользователя перепроверять промежуточные полусырые шаги. Сначала закончить логический пакет и самостоятельно проверить.

## Документирование после изменений

После каждого существенного изменения:

1. Обновить изменившиеся факты, статусы, блокеры и следующие действия в `PROJECT_STATE.md`; указать источник и дату.
2. Добавить новую запись в конец `PROJECT_HISTORY.md`. Старые записи не переписывать и не удалять.
3. Если появилось постоянное правило или новый повторяющийся риск — обновить `AGENTS.md`.
4. Коммит документации должен входить в тот же законченный пакет или следовать отдельным проверенным коммитом.
